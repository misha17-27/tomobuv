# Установка и переезд со старого сайта (Webasyst) на новый

Требования хостинга: **PHP 8.1+** (рекомендуется 8.3; расширения pdo_mysql, mbstring, gd, openssl, curl, zip, xmlreader,
dom, simplexml; желательно intl, exif), **MySQL 5.7 / 8.0 или MariaDB 10.3+**, Apache (или LiteSpeed) с mod_rewrite
(обычный cPanel/ISPmanager подходит), cron, доступ по SSH (или разовые задания cron — см. ниже).
Установка «с нуля» по этой инструкции проверена на MariaDB 10.3, MySQL 5.7 и MySQL 8.0 (строгий режим sql_mode по умолчанию), PHP 8.1 и 8.3.

`curl` — для загрузки прайсов и фото по ссылке и WhatsApp-уведомлений (без него работает, но фото грузятся по одному); `zip`, `xmlreader`, `dom`, `simplexml` —
для импорта XLSX/XML/YML. Что подключено на хостинге — видно в админке: «Состояние системы».

**PHP в командной строке** должен быть той же версии, что и у сайта: `php -v` (на cPanel часто нужен полный путь,
например `/opt/cpanel/ea-php83/root/usr/bin/php`, на ISPmanager — `/opt/php83/bin/php`). Этот же путь — в заданиях cron.

## 1. Подготовка (старый сайт продолжает работать)

1. Создайте на хостинге **две базы**: `tomobuv` (новая) и `tomobuv_old` (копия старой, нужна только для переноса).
2. Загрузите свежий дамп старой базы в `tomobuv_old` (phpMyAdmin → Импорт или `mysql tomobuv_old < tomobuv_db.sql`).
3. Залейте код (из GitHub) в папку, например `/home/USER/tomobuv/`.
   - Лучший вариант: корень домена (DocumentRoot) → папка `public/`.
   - Если панель не даёт сменить корень — положите проект целиком в `public_html`: корневой `.htaccess`
     сам направит запросы в `public/` и закроет служебные папки.
4. Скопируйте `config/config.example.php` → `config/config.php` и заполните: `base_url` (`https://tomobuv.com.ua`,
   на время проверки — временный адрес), доступы к обеим базам, `app_key` (случайная строка 64 символа:
   `php -r "echo bin2hex(random_bytes(32));"`), почту (`mail.admin_to`; SMTP можно и позже в админке, см. ниже).
   `debug` — **false**, `images.remote_base` — **пусто** (фото берутся из `public/wa-data/`, см. ниже).
5. Права на запись: `storage/` (и вложенные), `public/uploads/` и `public/wa-data/` — 775 (миниатюры фото создаются
   в `public/wa-data/public/shop/products/`). `config/config.php` после заполнения — 640 (только чтение для остальных).
   `bin/install.php` сам создаёт папки в `storage/` и предупреждает, если записи нет.
6. Лимиты PHP: в проекте есть `public/.user.ini` — `upload_max_filesize = 16M`, `post_max_size = 32M`,
   `memory_limit = 256M`, `max_execution_time = 120` (прайсы и фото из админки, импорт). На PHP-FPM/FastCGI
   (обычно на cPanel/ISPmanager) хостинг подхватит его сам в течение 5 минут; если PHP работает модулем Apache —
   выставьте те же значения в панели («Настройки PHP» / «Select PHP Version → Options»).
   Проверка: админка → «Состояние системы» → «Размер загрузки».

## 2. Перенос данных

Из папки проекта (`cd /home/USER/tomobuv`), строго по порядку — каждая команда должна закончиться без ошибок:

```bash
php bin/install.php            # создать таблицы новой базы (≈2–6 с)
php bin/import-webasyst.php    # перенести всё (≈1–2 минуты на 107 тыс. товаров; на MySQL 8 — дольше, чем на MariaDB)
php bin/i18n-seed-uk.php       # украинская версия: переводы из database/i18n/uk/ → база (≈20–40 с)
php bin/create-admin.php you@mail.com НовыйПароль admin   # свой вход в админку (пароль от 10 символов)
```
- `install.php` можно запускать повторно (и нужно — после обновления кода: добавит новые таблицы/колонки/индексы).
  Строка «часть ждёт следующих миграций — повтор в конце» — норма: такие файлы выполняются ещё раз после остальных.
  Если в конце «Ошибок: N» — дальше не идите, пришлите вывод разработчику.
- Нет SSH — добавьте в панели разовое задание cron на ближайшую минуту с той же командой и выводом в файл,
  например `cd /home/USER/tomobuv && php bin/install.php > storage/install.txt 2>&1`, дождитесь, прочитайте файл,
  удалите задание; затем так же остальные команды по одной.

Сотрудники старой админки Webasyst входят в новую (`/admin/`) со своим прежним e-mail/логином/телефоном и паролем
(все — с полными правами). Сразу после переноса откройте «Сотрудники» и отключите лишних или сделайте их менеджерами.
Клиенты входят в кабинет со старыми паролями (при первом входе пароль перешифровывается).

**Фото товаров**: скопируйте со старого сервера папки
`wa-data/public/shop/products/`, `wa-data/protected/shop/products/`, `wa-data/public/shop/brands/`,
`wa-data/public/shop/wmimageincatPlugin/`, `wa-data/public/shop/themes/balance/img/`, `wa-data/public/site/`, `wa-data/public/blog/`
в `public/wa-data/` нового сайта (адреса картинок сохраняются 1-в-1 — позиции в Google Картинках не теряются).
Проще всего — архивом через SSH/файловый менеджер: `tar czf wa-data.tgz wa-data` на старом сервере.
После распаковки удалите из `public/wa-data/` служебные файлы Webasyst — `.htaccess` (кроме `wa-data/protected/.htaccess`)
и `*.php` (например, `wa-data/public/shop/products/thumb.php`): `find public/wa-data -name '*.php' -delete` и
`find public/wa-data/public -name .htaccess -delete`. Иначе старый `.htaccess` перехватит создание миниатюр
(PHP в `wa-data/` всё равно не исполняется — `public/.htaccess` запрещает, но миниатюры не создадутся).

## 3. Cron

```
0 * * * *  php /home/USER/tomobuv/bin/cron.php >/dev/null 2>&1   # очистка кэша, корзин, сессий; публикация отложенных статей (раз в час)
```
Вместо `php` — полный путь к PHP нужной версии (см. «PHP в командной строке» выше). Что cron работает — видно
в «Состоянии системы» (строка «Cron»).

Автоимпорт прайса поставщика по расписанию (необязательно): в админке «Импорт / экспорт» сохраните настройки
как профиль со ссылкой на файл поставщика и добавьте задание, например каждую ночь в 3:30:
```
30 3 * * *  php /home/USER/tomobuv/bin/import.php ID_профиля >> /home/USER/tomobuv/storage/logs/import-cron.log 2>&1
```

Ночная перестройка индекса каталога (необязательно, но рекомендуется): после каждой правки товара индекс и счётчики
фильтров обновляются точечно; если один товар одновременно правят из админки и импорт, счётчики фильтров могут
разойтись на единицу-другую — ночная полная перестройка их выравнивает:
```
0 4 * * *  php /home/USER/tomobuv/bin/reindex.php >> /home/USER/tomobuv/storage/logs/reindex-cron.log 2>&1
```
Длительность на полной базе (107 тыс. товаров, 113 категорий, 243 тыс. строк индекса, 843 тыс. значений характеристик):
~4,4 с (замер на копии базы, MariaDB 10.3); на слабом хостинге — дольше. Перестройка идёт одной транзакцией: пока она
не закончилась, витрина показывает прежний полный индекс, потом сразу новый — запускать можно в любое время.
Сохранения товаров в админке и пачки импорта в это время не теряются: товар записывается сразу, а его строки индекса —
после перестройки (блокировка записи индекса, GET_LOCK MySQL). Перестройки идут по одной (блокировка
`storage/cache/reindex.lock` — общая для `bin/reindex.php`, кнопки «Перестроить индекс каталога» и «Завершения» импорта;
второй запуск ждёт первый до 10 минут); импорт на это время показывает «Идёт перестройка индекса каталога» и продолжает сам,
шаг импорта, попавший на взаимную блокировку InnoDB, повторяется без сообщения об ошибке (запись в `storage/logs/app-*.log`).
Прав CREATE/DROP/LOCK TABLES перестройка не требует — только SELECT/INSERT/UPDATE/DELETE. С binlog в формате STATEMENT
(редкость: MySQL 5.7+ по умолчанию ROW, MariaDB — MIXED) она идёт в REPEATABLE READ и дольше держит строки товаров.

## Почта и WhatsApp

- **Почта** (письма покупателю о заказе, уведомления о заказах и заявках): админка → «Почта (SMTP)» — адрес для
  уведомлений, отправитель и SMTP (например, Gmail: `smtp.gmail.com`, порт 465, SSL, логин — адрес, пароль —
  «пароль приложения» Google), кнопка «Отправить тестовое письмо». Без SMTP письма идут через `mail()` хостинга
  и часто попадают в спам. То же можно задать в `config/config.php` (`mail.*`) — значения из админки главнее.
  Ошибки отправки не мешают оформлению заказа и пишутся в `storage/logs/`.
- **WhatsApp** (новые заказы, «купить в 1 клик», по желанию — заявки): админка → «Настройки → WhatsApp» —
  номера получателей и сервис: Green-API (ваш WhatsApp по QR-коду: idInstance, apiTokenInstance) или WhatsApp Cloud API
  от Meta (Phone number ID, токен, при необходимости шаблон). Кнопка «Отправить тестовое сообщение», журнал отправок — там же.
  Хостинг должен разрешать исходящие HTTPS-запросы (на shared-хостинге обычно разрешены).

## 4. Проверка перед переключением

- Откройте сайт по временному адресу/поддомену, пройдите: главная → категория → фильтр → товар → корзина → оформление.
- Сверка SEO со старым сайтом: `python tools/seo-compare.py --new https://временный-адрес --sample 300`
  (title, description, keywords, h1, коды ответов должны совпасть).
- Обход ссылок: `python tools/crawl.py https://временный-адрес --limit 700 --nocache` и то же с `--start /ua/`
  (битые ссылки, ошибки PHP, ссылки с украинской версии на русскую и наоборот).
- Админка `/admin/`: заказы, товары, импорт.

## 5. Переключение

1. Ещё раз выгрузите свежую базу старого сайта в `tomobuv_old` и запустите `php bin/install.php`,
   `php bin/import-webasyst.php`, затем `php bin/i18n-seed-uk.php` (перенесутся новые заказы и товары, накатятся украинские переводы).
   Повторный перенос **заменяет** данными старого сайта каталог (категории, бренды, характеристики, товары),
   страницы, блог, баннеры, отзывы о магазине, заказы и основные настройки магазина (название, телефоны, SEO-шаблоны,
   валюты, способы доставки и оплаты) — правки этих разделов в новой админке до переключения пропадут, делайте их после.
   **Сохраняются**: клиенты и сотрудники, зарегистрированные на новом сайте, и уже сменённые пароли, промокоды,
   редиректы, заявки, профили импорта, настройки почты/SMTP, WhatsApp, IP-доступа к админке, ссылки на соцсети.
2. Досинхронизируйте `wa-data` (новые фото).
3. Направьте домен на новую папку (или поменяйте местами папки). Включите редирект на `https://tomobuv.com.ua`
   (с http, www и чужих Host) — в панели хостинга или в `public/.htaccess` (раскомментируйте блок «Принудительно HTTPS
   и основной домен»), см. «Чек-лист перед запуском».
4. В Google Search Console отправьте `https://tomobuv.com.ua/sitemap.xml`.

## Cloudflare и другие прокси перед сайтом

Если сайт открывается через Cloudflare (или перед Apache стоит nginx хостинга), PHP видит адрес прокси, а не посетителя:
все посетители выглядят одним IP, и лимиты попыток входа, отправки форм и заказов становятся общими на всех,
а в журналах и заказах — IP прокси. Чтобы брать настоящий IP из `X-Forwarded-For` / `CF-Connecting-IP`,
перечислите адреса прокси в `config/config.php`:

```php
// все подсети IPv4 и IPv6 со страницы https://www.cloudflare.com/ips/ (список на 28.09.2026; изредка меняется — сверяйте)
'trusted_proxies' => [
    '173.245.48.0/20', '103.21.244.0/22', '103.22.200.0/22', '103.31.4.0/22', '141.101.64.0/18', '108.162.192.0/18',
    '190.93.240.0/20', '188.114.96.0/20', '197.234.240.0/22', '198.41.128.0/17', '162.158.0.0/15', '104.16.0.0/13',
    '104.24.0.0/14', '172.64.0.0/13', '131.0.72.0/22',
    '2400:cb00::/32', '2606:4700::/32', '2803:f800::/32', '2405:b500::/32', '2405:8100::/32', '2a06:98c0::/29', '2c0f:f248::/32',
    // '127.0.0.1',   // если перед Apache ещё и nginx хостинга
],
```
Заголовки принимаются **только** от этих адресов — без списка их игнорируем (подделать их может кто угодно).
Если прокси нет — оставьте `trusted_proxies` пустым. Проверка: «Состояние системы» → «IP посетителей»
(там же видно, если запрос пришёл через прокси, а список не задан). HTTPS за прокси определяется по `X-Forwarded-Proto`
(Cloudflare ставит его сам); режим SSL в Cloudflare — «Full (strict)», не «Flexible».

## Чек-лист перед запуском

- [ ] `config/config.php`: `'debug' => false`, `'env' => 'production'`.
- [ ] Свой `app_key` (не из локальной копии): `php -r "echo bin2hex(random_bytes(32));"`. Он подписывает ссылки на заказы из писем —
      после смены старые ссылки перестанут открываться.
- [ ] `'base_url' => 'https://tomobuv.com.ua'` (без слэша в конце). От него зависят canonical, sitemap, robots.txt, ссылки в письмах
      и кэш страниц (кэшируются только запросы на этот домен, с www или без). После любой правки `config.php` — `php bin/cache-clear.php`.
- [ ] На хостинг **не заливать** `config/config.php` локальной копии, `storage/dev-*.txt` (учётки для разработки) и содержимое `storage/`
      (кэш, сессии, журналы, загрузки) — `bin/install.php` создаст папки сам. Проверка на сервере: `ls storage/dev-*` — пусто.
- [ ] Cron `bin/cron.php` раз в час (раздел 3); в «Состоянии системы» строка «Cron» — зелёная.
- [ ] Сайт за Cloudflare/прокси — заполнен `trusted_proxies` (раздел выше).
- [ ] Редирект на `https://tomobuv.com.ua` с `http://`, с `www.` и с любых чужих Host (сайт по умолчанию на IP сервера):
      в панели хостинга (основной домен + «перенаправлять на HTTPS») или блок «Принудительно HTTPS и основной домен» в `public/.htaccess`
      (для проекта в `public_html` — тот же файл). Проверка: `curl -I http://tomobuv.com.ua/`, `curl -I https://www.tomobuv.com.ua/` и
      `curl -I -H "Host: example.com" http://IP-сервера/` — `301` на `https://tomobuv.com.ua/…`.
- [ ] Лимиты загрузки: `upload_max_filesize` от 16M, `post_max_size` от 32M (`public/.user.ini` или панель, раздел 1, п. 6);
      в «Состоянии системы» строка «Размер загрузки» — зелёная.
- [ ] Повторный `php bin/import-webasyst.php` **затирает** каталог, страницы, блог, баннеры, отзывы, заказы и основные настройки магазина
      (раздел 5) — правки в новой админке делайте только после финального переноса.
- [ ] После каждого обновления кода: `php bin/install.php` — применит новые файлы `database/migrations/*.sql` (колонки, индексы;
      повторный запуск безопасен, в конце — «Готово: N SQL-команд», без строки «Ошибок»), затем `php bin/cache-clear.php`. Без этого новые функции падают
      с ошибкой «Unknown column».
- [ ] «Состояние системы»: нет строк «нужно исправить»; строки «Закрыт адрес …» — 403/404 (служебные папки не отдаются).
- [ ] «Сотрудники»: свой администратор создан (`php bin/create-admin.php`), лишние перенесённые учётки отключены или стали менеджерами.

## Скорость

- Кэш готовых страниц включён по умолчанию (`cache.pages`). После правок в админке кэш сбрасывается автоматически;
  вручную — кнопка «Очистить кэш» в админке или `php bin/cache-clear.php`.
- Индекс каталога перестраивается автоматически после изменений; полностью — `php bin/reindex.php`. После обновления, которое
  добавило `database/migrations/catalog-index-sig.sql`, выполните `php bin/reindex.php` один раз: до этого точечная переиндексация
  (сохранение товара, импорт) верная, но медленнее — пересчитывает фильтры категорий товара целиком.
- Включите в панели хостинга OPcache (обычно включён) и PHP 8.2+.
